## 轨迹回放（微信小程序端）：修复安卓车标闪动 + 未播放灰色虚线 / 已播放蓝色实线

- 页面：`pages/playBack/playBack.uvue`。参考实现：Flutter 端 `car_flutter/lib/views/vehicle/playback/`（`playback_controller.dart` 的 `playedRoutePoints` / `unplayedRoutePoints`，`playback_view.dart` 的 PolylineLayer 样式）。
- 按用户要求：**不做** Flutter 端的"车标跟随开关"（`_FollowFab`），本项目保持始终跟随。

### 问题 1：安卓上车标一直闪动

- 根因（外部事实依据）：微信小程序原生地图在**安卓机上每次收到 `markers` 都会销毁重建整个 marker 覆盖物**（含 `callout`），表现为明显跳闪，iOS 无此现象。微信官方社区原始反馈与共识解法是"不要 setData，用 `MapContext.translateMarker`"。
- **关键约束（已核实）**：uni-app x 的 `uni.createMapContext()` 在**微信小程序端不支持 `translateMarker`**（官方兼容性表：微信 ✗ / 支付宝 4.31 / Android 4.31 / iOS 4.61），因此本项目无法绕开 setData，只能压低下发次数。
- 原实现每 50ms（20 帧/秒）新建 `markers` 数组并整体替换，还把角度阈值（2°）设得几乎不生效，等于每帧重建一次覆盖物。
- 改法：**按可见位移下发**（新增 `MARKER_MOVE_DEADBAND_PX = 2.0`、`MARKER_FORCE_PUSH_INTERVAL_MS = 1000`）。
  - 新增 `getMetersPerPixelOfScale()` / `shouldPushMarkerPosition()` / `markMarkerPositionPushed()` / `resetMarkerPushTracking()`，全部包在 `#ifdef MP-WEIXIN` 内。
  - `updateCarPosition()` 开头做像素死区判断，不足 2px 就整帧 return —— **车标与地图中心必须成对下发**，否则车标会相对镜头滞后、复现"跑出屏幕再弹回"。
  - 帧间隔仍是 50ms（插值精度不受影响），只是绝大多数帧不再跨线程通信：全览缩放下 1px 约上百米，下发频率从 20 次/秒降到约 1 次/秒；用户放大到 17 级时 2px 死区约每 0.3 秒触发一次，仍然跟手。
  - 兜底"每秒至少下发一次"，避免高倍缩放下死区长时间凑不满导致镜头停滞。
  - 重置点：`clearTrackDisplay()`（换轨迹）、`resetPlayback()`（回起点）调 `resetMarkerPushTracking()`；`focusMapOnVehicle()` 调 `markMarkerPositionPushed()` 避免起播重复下发。
- **约定**：微信端优化"跟随手感"时，优先压低下发频率（像素死区），而不是降帧率 —— 帧率只影响插值精度，跨线程通信次数才是闪动的直接原因。

### 问题 2：未播放灰色虚线 / 已播放蓝色实线（对齐 Flutter）

- 改动仅在 `#ifdef MP-WEIXIN` 的 `updatePolyline()`：未播放 `#999999` / `width 3` / `dottedLine: true`；已播放 `#1890FF` / `width 3` / `dottedLine: false` / `arrowLine: false`；两条 `borderWidth` 由 1 改 0（虚线加白色描边会糊成一片）。
- 两条线**线宽相同**且蓝色在数组后面（绘制更上层），正好完全盖住灰色虚线已走过的那一段 —— 这是 Flutter 端 `playback_view.dart:133` 注释里明确的做法。
- App 端原本就是"灰色虚线 + 蓝色实线"，因此这次改完三端表现一致，无需改动 App 分支。

### 待验证 / 后续旋钮

- 需真机确认：① 安卓车标不再闪动且跟手；② 未播放为灰虚线、已播放为蓝实线、线宽一致。

## 第二轮：修复"安卓播放时车标和地图一顿一顿"（上一轮像素死区方案的副作用）

- **根因**：上一轮把 `markers` 的像素死区门控**同时套在了地图中心上**，而这两者成本差一个数量级。编译产物（`unpackage/dist/dev/mp-weixin/pages/playBack/playBack.wxml`）证实它们是**三个独立顶层绑定**：
  ```
  latitude="{{d}}"  longitude="{{e}}"  markers="{{f}}"
  ```
  - `center` = 2 个数字，极轻，且**不会触发安卓端覆盖物重建** → 可以放心逐帧（20 帧/秒）下发；
  - `markers` = 整个数组，安卓会销毁重建 marker 覆盖物层 → 必须节流。
- 于是低缩放下（整条轨迹全览，1px≈上百米）死区长期凑不满 2px，被 `MARKER_FORCE_PUSH_INTERVAL_MS = 1000` 兜底成**每秒下发一次** —— 车标和镜头一起每秒"顿"一下，观感正是用户反馈的"一顿一顿"。
- **改法**：把地图中心更新从死区判断**之前**提出，`updateCarPosition()` 里改为：
  1. `if (isPlaying.value) { center.latitude = ...; center.longitude = ... }` —— **每帧执行**（仅播放中，未播放仍保持全览）；
  2. 之后才 `if (!shouldPushMarkerPosition()) return` 拦截 `markers` 下发。
  两者彻底解耦：**中心求流畅、marker 求不闪**。车标最多偏离画面中心 2px，肉眼不可分辨。
- **第二个卡顿源：帧定时器漂移**。原 `setTimeout(renderFrame, PLAYBACK_FRAME_INTERVAL_MS)` 是递归调用，每帧的调度延迟会累积，实际帧率明显低于设定值。改为**自校正调度**：以本段 `startedAt` 为基准算下一帧目标时刻，落后则 `delay = 0` 立即补帧：
  ```ts
  const nextFrameAt = startedAt + (Math.floor((Date.now() - startedAt) / PLAYBACK_FRAME_INTERVAL_MS) + 1) * PLAYBACK_FRAME_INTERVAL_MS
  const delay = nextFrameAt - Date.now()
  playbackTimer = setTimeout(() => { renderFrame?.() }, delay > 0 ? delay : 0)
  ```
  （轨迹插值 `progress` 本就基于绝对时间，位置始终准确，受影响的只是帧率抖动。）
- **重要约定（写给后续维护）**：在微信小程序端做地图动画时，**必须区分"镜头（center）"与"覆盖物（markers/polyline）"两类成本**——前者可以逐帧下发求流畅，后者必须节流求不闪。把两者绑进同一个节流门控会同时拿到"闪动"和"卡顿"两个坏结果。
- 校验：三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译预处理后括号配平与符号存在性均通过；`paren=2` 是校验器把注释内中文圆括号计入的**既有误报**，与 `git show HEAD:` 基线版本数值完全一致，本次未引入新问题。

## 第三轮：修复"镜头已丝滑、但车标仍卡顿"（第二轮死区参数过粗的副作用）

- **根因**：第二轮虽然把镜头和车标解耦了，但车标的节流参数本身太粗 —— `MARKER_MOVE_DEADBAND_PX = 2.0` 死区太大、`MARKER_FORCE_PUSH_INTERVAL_MS = 1000` 兜底太长。实测推算（zoom 12~17 × 30/60/120km/h）显示：**旧逻辑在几乎所有缩放级别下车标都是 1000ms 才下发一次**，跳动2px 左右。镜头 20Hz 丝滑、车标 1Hz 跳动 → 车标相对底图每秒滑行一次再跳回，正是用户反馈的"车标在地图上卡顿着运动"。
- **关键认知**：像素死区的正确量级不是"肉眼勉强看不见"，而应该是**亚像素（0.5px）**。只要单次跳动小于1 个像素，无论下发频率是 1Hz 还是 15Hz，视觉上都是连续的；反之2px 的跳动在 1Hz 下就是肉眼明显的顿挫。
- **改法**：`shouldPushMarkerPosition()` 改为**双约束**判定（两者缺一不可）：
  1. **频率上限** `MARKER_MIN_PUSH_INTERVAL_MS = 66`（约 15Hz）—— 距上次下发不足则跳过，这是防闪动的主要闸门；
  2. **位移死区** `MARKER_MOVE_DEADBAND_PX = 2.0 → 0.5`（亚像素）；
  3. 兜底 `MARKER_FORCE_PUSH_INTERVAL_MS = 1000 → 250`。
  顺序很关键：**先判兜底、再判频率上限、最后判死区**。
- 实测效果（跳动量对比）：zoom14/60km/h 由`1000ms跳2.01px` 变为 `250ms跳0.50px`（**4 倍**）；zoom16/60km/h 由 `250ms跳2.01px` 变为 `100ms跳0.80px`（2.5 倍）。全场景跳动量降到 1/4~1/2.5。
- **第二个卡顿源：折线重绘占用动画帧关键路径**。`updatePolyline()` 是 O(n) 的切片+坐标转换+抽稀，长轨迹下可达几十毫秒，且与车标**共用同一条跨线程通道**——原先在帧内同步执行，会推迟本帧车标的 setData，表现为车标周期性顿挫。两处优化：
  1. **抽稀顺序反转**：原实现先 `toMpPoints()` 为**每个**原始点建对象、再丢掉大部分（长轨迹下白建上千个对象）。改为 `toThinnedMpPoints()` **先按索引抽稀、再转换**，只创建真正要发的那 400 个对象。点数上限 `MAX_POLYLINE_POINTS` 由 500 降为 400。
  2. **移出关键路径**：帧内只做`const polylineDue = ...` 的整数比较（开销可忽略），把真正的 `updatePolyline()` 放进紧随其后的独立 `setTimeout(..., 0)`；此时本帧车标与镜头的 setData 已被收集发出，不再互相抢时间。带 `sessionId` 校验，播放已停止则跳过。
  3. `POLYLINE_RENDER_INTERVAL_MS` 由 500 放宽到 **1000**：折线只需让"已走/未走"分界大致跟上，车标本来就压在分界前面，两者最多差一根线宽，没必要和车标同频。
- **重要约定（写给后续维护）**：像素死区要用**亚像素**（0.5px 量级），不能用"肉眼勉强看不见"（2px）当标准 —— 后者在低频下发下就是可见的顿挫。另外，折线这类 O(n) 的重绘**绝不能放在动画帧的关键路径上**，否则会周期性推迟车标下发。
- 校验：三平台条件编译预处理后括号配平通过（`paren=2` 仍为注释内中文圆括号导致的既有误报，与基线一致）；微信端新增符号未泄漏到 App 分支；App 端仍用未抽稀的 `toMpPoints()`，行为不变。

## 第四轮：修复"车标仍一顿一顿"+"蓝线到终点但车标还差一段"+"不闪动地实现高频下发"

### 问题 1 根因：66ms 时间闸门与 50ms 帧栅格不对齐（节流失配）

- 第三轮引入的 `MARKER_MIN_PUSH_INTERVAL_MS = 66`（约 15Hz 上限）与 `PLAYBACK_FRAME_INTERVAL_MS = 50`（20Hz）**不在同一栅格上**：66 落在相邻两帧中间，导致刚推完的那一帧必然撞上 `elapsed < 66` 被拦下，实际频率被压成 **100ms/次（10Hz）**。
- 而镜头是每帧 20Hz。**两者节奏失配就是"车标一顿一顿"的直接原因** —— 底图 20Hz 平滑滑过，车标 10Hz 跳一下。
- **改法**：删掉 `MARKER_MIN_PUSH_INTERVAL_MS` 与 `shouldPushMarkerPosition()` 里的时间闸门，只保留**纯位移死区**（`MARKER_MOVE_DEADBAND_PX = 0.5`）+兜底（`MARKER_FORCE_PUSH_INTERVAL_MS = 250`）。车标与镜头重新同频 20Hz。
- 实测（zoom 16~17、60~120km/h）：间隔由 100ms → 50ms（**10Hz → 20Hz**），单次跳动由 1.60~3.21px → 0.80~1.60px。

### 问题 3 的解法：靠"减轻单次下发内容"而不是"降低下发频率"来防闪动

- 之前的防闪动思路是**降频**，但降频直接换来卡顿——这是一对矛盾。
- 关键认识：闪动的本质是**单次重建的视图数**，不是频率。微信端每收到一次 `markers` 就销毁重建整个 marker 覆盖物层，**重建成本与数组里 marker 数量、每个 marker 挂多少 callout 成正比**。
- 原数组是 `[车标, 起点+callout, 终点+callout]` → 每次下发重建 **3 个视图 + 2 个气泡**。
- **改法**：新增 `PLAYBACK_MARKER_LITE = true`（`#ifdef MP-WEIXIN`）。播放期间 `applyPlaybackLiteMarkers()` 只下发车标 1 个 marker，**单次重建成本降到约 1/3**；暂停/结束时由 `applyFullMarkers()` 把起终点补回。为此把 `initCarMarker()` 里的 `startMarker` / `endMarker` 从局部变量提为外层 `let` 引用，否则播放中被剔除后无法补回。
- 这样车标得以**在 20Hz 下发的同时不闪**，问题 1 与问题 3 同时解决。

### 问题 2 根因：播放结束时最后一帧被死区拦下，且此后不再有帧来补正

- `finishPlayback()` → `pausePlayback()` 会 `clearPlaybackTimer()`，**定时器清空后不再有帧**。而最后一帧的 `updateCarPosition()` 可能被 `shouldPushMarkerPosition()` 拦下（距上次下发不足死区/兜底），于是**车标永久停在最后一次推送的位置**；而 `updatePolyline()` 不受该节流约束，直接把蓝线画到终点 → **蓝线已到终点、车标还差一小段**。倍速越高、末段越短，越容易被触发。
- **改法（三处强制对齐）**：
  1. `updateCarPosition()` 增加 `force : boolean` 参数，`force = true` 时跳过节流。函数签名改为 `updateCarPosition(force : boolean)`，三个调用点全部显式传参：`renderPlaybackIndex()` 与 `pausePlayback()` 传 `true`，动画帧内传 `false`。
  2. `renderPlaybackIndex()`：这是"跳变后的确定值"（段末 / 重置 / 载入完成），改为 `updateCarPosition(true)`。
  3. `pausePlayback()`：暂停与播放结束的共同出口，在此 `resetMarkerPushTracking()` + `updateCarPosition(true)` + `applyFullMarkers()` 一次性收尾对齐（车标强制到位 + 起终点补回）。
- 效果：车标与终点差距从"最多 66ms 的位移（倍速 30x 时末段仅 16.7ms，差距最明显）"降为 **0**。

### 本轮重要约定（写给后续维护）

1. **节流阈值必须与帧间隔对齐**。像 `MARKER_MIN_PUSH_INTERVAL_MS = 66` 这种"独立取值"会与 50ms 帧栅格产生拍频，把 20Hz 压成 10Hz 而非预期的 15Hz。要限频就让阈值等于帧间隔的整数倍，否则干脆不设时间闸门、只用位移死区。
2. **"防闪动"与"防卡顿"在微信小程序地图上是对立的**，必须换维度破局：不要靠降频防闪，而要靠**减少单次下发的视图数**（播放时剔除静止的起终点 marker 及其 callout），从而在高频下也不闪。
3. **镜头与覆盖物的节流门控必须分离**，且**任何"清空定时器"的收尾路径都要强制补正最后一帧**——否则会出现"动画已结束、图形差一小段"的永久性错位。

### 校验

- 三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译预处理后括号配平通过（`paren=2` 仍为校验器把注释内中文圆括号计入的既有误报，与 `git show HEAD:` 基线一致）。
- 微信端新增符号（`applyFullMarkers` / `applyPlaybackLiteMarkers` / `startMarker` / `endMarker`）在 App 分支均可见且不依赖微信端常量；`PLAYBACK_MARKER_LITE` 与 `applyPlaybackLiteMarkers` 已包进 `#ifdef MP-WEIXIN`，剥离注释后确认**未泄漏到 App 分支**。

## 第五轮：车标闪动的根治（放弃 markers 路线，改用 cover覆盖物）

### 为什么前三轮的所有努力都不可能成功

- 用户反馈：车标与镜头已完全同频、结束精确落在终点、暂停后起终点正常，但**车标仍在长距离直线段不停闪动**。
- 根因（三轮方案的共同天花板）：**闪动的物理来源只有一个 —— 微信小程序端每收到一次 `markers` 赋值，安卓原生 SDK 就销毁并重建整个 marker 覆盖物层**，那一帧的销毁残留就是闪动。
- 前三轮用的都是"**降频 + 减轻单次重建成本**"（像素死区、时间闸门、`PLAYBACK_MARKER_LITE` 剔除起终点）。这些只能让闪动**变少**，无法让它**归零**，因为"重建"这个动作本身从未被取消。
- 为什么偏偏是长距离直线段最明显：直线段车速高 → 每帧位移远超 0.5px 死区 → **每一帧都必然越过死区、每帧都下发** → 闪动频率达到理论上限（20 次/秒）。这恰好是前几轮参数调优无法覆盖的最坏工况。

### 本轮方案：把播放期车标整体移出原生 markers 图层

- 关键突破：**车标根本不需要是 marker**。播放时车标恒定位于屏幕正中，那么它可以是一个**普通 `view` 覆盖物**（`.car-overlay` + `image`，50rpx 见方，`position:absolute` 四边贴合 + flex 居中），盖在 map 之上。
- 可行性依据（已核实）：uni-app x 官方文档明确 `cover-view` 在 **app / web / 微信小程序上已废弃，直接用 `view` 即可**（微信基础库 2.8.3 起 map 支持同层渲染）；且本项目 `sub-navBar`（`z-index:100` 的普通 view）本来就压在 map 之上正常显示，编译产物 `playBack.wxml` 证实它是 map 的**兄弟节点**而非子节点 —— 同层渲染在本项目已验证可用。
- 于是播放期的职责彻底分离：
  - **只有地图在动**（`center` 每 50ms 下发两个数字，极轻、不触发覆盖物重建）；
  - **车标钉在正中不动**，视觉上二者完全同频；
  - **`markers` 数组在整个播放过程一次都不再被赋值** → 安卓端零图层重建 → **闪动彻底消除**。
- 车标朝向仍需变化，因此覆盖层保留 `transform: rotate()`，用 2° 死区（复用 `MARKER_ROTATION_UPDATE_THRESHOLD`）。直线段朝向恒定，连这点 setData 都不会发生。

### 代码改动要点

- 模板：`map` 之后、`sub-navBar` 之前新增 `#ifdef MP-WEIXIN` 的 `.car-overlay`；新增 `showCarOverlay` / `carOverlayIcon` / `carOverlayRotation` 三个状态。
- `updateCarPosition()`：在 `if (isPlaying)` 更新 center 之后**立刻插入提前 `return`** —— 播放期只刷覆盖层朝向，完全不碰 `markers`。这是全文件最关键的一处改动。
- `startPlayback()`：`showCarOverlay = true` + `carOverlayRotation = 当前角度` + `markers.value = markers.value.slice(1)`（剔除原生车标，保留静止的起终点）。交接发生在同一帧，视觉无缝。
- `pausePlayback()`：`showCarOverlay = false` + `updateCarPosition(true)` + `applyFullMarkers()`。**关键**：必须先让原生 markers 车标精确落到最后一个渲染点，否则覆盖层消失后会看到车标错位一小段。
- `renderPlaybackIndex()` 的 `if (!isPlaying.value) applyFullMarkers()` 守卫是**正确且必须保留**的 —— 播放中一旦在这里把车标补回 `markers`，闪动立刻回来。
- 新增 `shortestAngleDiff(from, to)` 工具函数（环形量按最短路径比较，-180~180）。原先 359°→1° 会被误判为 -358° 转角，导致每帧都触发朝向重绘。
- 清理了彻底失效的符号：`shouldPushMarkerPosition()` / `markMarkerPositionPushed()` / `resetMarkerPushTracking()` / `PLAYBACK_MARKER_LITE` / `applyPlaybackLiteMarkers()` / `MARKER_MOVE_DEADBAND_PX` / `MARKER_FORCE_PUSH_INTERVAL_MS` 及配套的 `lastPushedLat` 等变量。`getMetersPerPixelOfScale()` 暂无调用方但保留（视野计算相关，可能复用）。

### 本轮最重要的一条工程结论（写给后续维护）

1. **在微信小程序地图上，"防闪动"和"防卡顿"无法靠调参同时满足** —— 因为闪动源于 `markers` 的**原生图层重建**，而降频必然带来滞后与顿挫。唯一的出路是**换维度：让需要高频变化的东西彻底离开原生覆盖物图层**。
2. 判断某个视觉元素该不该留在 `markers` 里，标准是：**它是否需要高频变化**。需要高频变化（车标、跟随光标）就不要放进 `markers`；静止不动的（起终点、气泡、POI）才适合。
3. 由此可推广：地图上凡是"位置高频变化 + 视觉上可以由容器定位表达"的东西，都应该用**覆盖物 + 容器居中**表达，而不是原生 marker。项目里 `deviceList.uvue` 的聚合点同理，若后续也遇到闪烁，可考虑同样处理。
4. 交接（切换表示方式）必须在**同一帧**内完成，且旧表示要先精确落位再隐藏新表示，否则会出现一帧的错位。
