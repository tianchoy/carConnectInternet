## 轨迹回放（微信小程序端）：修复安卓车标闪动 + 未播放灰色虚线 / 已播放蓝色实线

- 页面：`pages/playBack/playBack.uvue`。参考实现：Flutter 端 `car_flutter/lib/views/vehicle/playback/`（`playback_controller.dart` 的 `playedRoutePoints` / `unplayedRoutePoints`，`playback_view.dart` 的 PolylineLayer 样式）。
- 按用户要求：**不做** Flutter 端的"车标跟随开关"（`_FollowFab`），本项目保持始终跟随。

### 问题 1：安卓上车标一直闪动

- 根因（外部事实依据）：微信小程序原生地图在**安卓机上每次收到 `markers` 都会销毁重建整个 marker 覆盖物**（含 `callout`），表现为明显跳闪，iOS 无此现象。微信官方社区原始反馈与共识解法是"不要 setData，用 `MapContext.translateMarker`"。
- **关键约束（已核实）**：uni-app x 的 `uni.createMapContext()` 在**微信小程序端不支持 `translateMarker`**（官方兼容性表：微信 ✗ / 支付宝 4.31 / Android 4.31 / iOS 4.61），因此本项目无法绕开 setData，只能压低下发次数。
- 原实现每 50ms（20 帧/秒）新建 `markers` 数组并整体替换，还把角度阈值（2°）设得几乎不生效，等于每帧重建一次覆盖物。
- 改法：**按可见位移下发**（新增 `MARKER_MOVE_DEADBAND_PX = 2.0`、`MARKER_FORCE_PUSH_INTERVAL_MS = 1000`）。
  - 新增 `getMetersPerPixelOfScale()` / `shouldPushMarkerPosition()` / `markMarkerPositionPushed()` / `resetMarkerPushTracking()`，全部包在 `#ifdef MP-WEIXIN` 内。
  - `updateCarPosition()` 开头做像素死区判断，不足 2px 就整帧 return —— **车标与地图中心必须成对下发**，否则车标会相对镜头滞后、复现"跑出屏幕再弹回"。
  - 帧间隔仍是 50ms（插值精度不受影响），只是绝大多数帧不再跨线程通信：全览缩放下 1px 约上百米，下发频率从 20 次/秒降到约 1 次/秒；用户放大到 17 级时 2px 死区约每 0.3 秒触发一次，仍然跟手。
  - 兜底"每秒至少下发一次"，避免高倍缩放下死区长时间凑不满导致镜头停滞。
  - 重置点：`clearTrackDisplay()`（换轨迹）、`resetPlayback()`（回起点）调 `resetMarkerPushTracking()`；`focusMapOnVehicle()` 调 `markMarkerPositionPushed()` 避免起播重复下发。
- **约定**：微信端优化"跟随手感"时，优先压低下发频率（像素死区），而不是降帧率 —— 帧率只影响插值精度，跨线程通信次数才是闪动的直接原因。

### 问题 2：未播放灰色虚线 / 已播放蓝色实线（对齐 Flutter）

- 改动仅在 `#ifdef MP-WEIXIN` 的 `updatePolyline()`：未播放 `#999999` / `width 3` / `dottedLine: true`；已播放 `#1890FF` / `width 3` / `dottedLine: false` / `arrowLine: false`；两条 `borderWidth` 由 1 改 0（虚线加白色描边会糊成一片）。
- 两条线**线宽相同**且蓝色在数组后面（绘制更上层），正好完全盖住灰色虚线已走过的那一段 —— 这是 Flutter 端 `playback_view.dart:133` 注释里明确的做法。
- App 端原本就是"灰色虚线 + 蓝色实线"，因此这次改完三端表现一致，无需改动 App 分支。

### 待验证 / 后续旋钮

- 需真机确认：① 安卓车标不再闪动且跟手；② 未播放为灰虚线、已播放为蓝实线、线宽一致。

## 第二轮：修复"安卓播放时车标和地图一顿一顿"（上一轮像素死区方案的副作用）

- **根因**：上一轮把 `markers` 的像素死区门控**同时套在了地图中心上**，而这两者成本差一个数量级。编译产物（`unpackage/dist/dev/mp-weixin/pages/playBack/playBack.wxml`）证实它们是**三个独立顶层绑定**：
  ```
  latitude="{{d}}"  longitude="{{e}}"  markers="{{f}}"
  ```
  - `center` = 2 个数字，极轻，且**不会触发安卓端覆盖物重建** → 可以放心逐帧（20 帧/秒）下发；
  - `markers` = 整个数组，安卓会销毁重建 marker 覆盖物层 → 必须节流。
- 于是低缩放下（整条轨迹全览，1px≈上百米）死区长期凑不满 2px，被 `MARKER_FORCE_PUSH_INTERVAL_MS = 1000` 兜底成**每秒下发一次** —— 车标和镜头一起每秒"顿"一下，观感正是用户反馈的"一顿一顿"。
- **改法**：把地图中心更新从死区判断**之前**提出，`updateCarPosition()` 里改为：
  1. `if (isPlaying.value) { center.latitude = ...; center.longitude = ... }` —— **每帧执行**（仅播放中，未播放仍保持全览）；
  2. 之后才 `if (!shouldPushMarkerPosition()) return` 拦截 `markers` 下发。
  两者彻底解耦：**中心求流畅、marker 求不闪**。车标最多偏离画面中心 2px，肉眼不可分辨。
- **第二个卡顿源：帧定时器漂移**。原 `setTimeout(renderFrame, PLAYBACK_FRAME_INTERVAL_MS)` 是递归调用，每帧的调度延迟会累积，实际帧率明显低于设定值。改为**自校正调度**：以本段 `startedAt` 为基准算下一帧目标时刻，落后则 `delay = 0` 立即补帧：
  ```ts
  const nextFrameAt = startedAt + (Math.floor((Date.now() - startedAt) / PLAYBACK_FRAME_INTERVAL_MS) + 1) * PLAYBACK_FRAME_INTERVAL_MS
  const delay = nextFrameAt - Date.now()
  playbackTimer = setTimeout(() => { renderFrame?.() }, delay > 0 ? delay : 0)
  ```
  （轨迹插值 `progress` 本就基于绝对时间，位置始终准确，受影响的只是帧率抖动。）
- **重要约定（写给后续维护）**：在微信小程序端做地图动画时，**必须区分"镜头（center）"与"覆盖物（markers/polyline）"两类成本**——前者可以逐帧下发求流畅，后者必须节流求不闪。把两者绑进同一个节流门控会同时拿到"闪动"和"卡顿"两个坏结果。
- 校验：三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译预处理后括号配平与符号存在性均通过；`paren=2` 是校验器把注释内中文圆括号计入的**既有误报**，与 `git show HEAD:` 基线版本数值完全一致，本次未引入新问题。

## 第三轮：修复"镜头已丝滑、但车标仍卡顿"（第二轮死区参数过粗的副作用）

- **根因**：第二轮虽然把镜头和车标解耦了，但车标的节流参数本身太粗 —— `MARKER_MOVE_DEADBAND_PX = 2.0` 死区太大、`MARKER_FORCE_PUSH_INTERVAL_MS = 1000` 兜底太长。实测推算（zoom 12~17 × 30/60/120km/h）显示：**旧逻辑在几乎所有缩放级别下车标都是 1000ms 才下发一次**，跳动2px 左右。镜头 20Hz 丝滑、车标 1Hz 跳动 → 车标相对底图每秒滑行一次再跳回，正是用户反馈的"车标在地图上卡顿着运动"。
- **关键认知**：像素死区的正确量级不是"肉眼勉强看不见"，而应该是**亚像素（0.5px）**。只要单次跳动小于1 个像素，无论下发频率是 1Hz 还是 15Hz，视觉上都是连续的；反之2px 的跳动在 1Hz 下就是肉眼明显的顿挫。
- **改法**：`shouldPushMarkerPosition()` 改为**双约束**判定（两者缺一不可）：
  1. **频率上限** `MARKER_MIN_PUSH_INTERVAL_MS = 66`（约 15Hz）—— 距上次下发不足则跳过，这是防闪动的主要闸门；
  2. **位移死区** `MARKER_MOVE_DEADBAND_PX = 2.0 → 0.5`（亚像素）；
  3. 兜底 `MARKER_FORCE_PUSH_INTERVAL_MS = 1000 → 250`。
  顺序很关键：**先判兜底、再判频率上限、最后判死区**。
- 实测效果（跳动量对比）：zoom14/60km/h 由`1000ms跳2.01px` 变为 `250ms跳0.50px`（**4 倍**）；zoom16/60km/h 由 `250ms跳2.01px` 变为 `100ms跳0.80px`（2.5 倍）。全场景跳动量降到 1/4~1/2.5。
- **第二个卡顿源：折线重绘占用动画帧关键路径**。`updatePolyline()` 是 O(n) 的切片+坐标转换+抽稀，长轨迹下可达几十毫秒，且与车标**共用同一条跨线程通道**——原先在帧内同步执行，会推迟本帧车标的 setData，表现为车标周期性顿挫。两处优化：
  1. **抽稀顺序反转**：原实现先 `toMpPoints()` 为**每个**原始点建对象、再丢掉大部分（长轨迹下白建上千个对象）。改为 `toThinnedMpPoints()` **先按索引抽稀、再转换**，只创建真正要发的那 400 个对象。点数上限 `MAX_POLYLINE_POINTS` 由 500 降为 400。
  2. **移出关键路径**：帧内只做`const polylineDue = ...` 的整数比较（开销可忽略），把真正的 `updatePolyline()` 放进紧随其后的独立 `setTimeout(..., 0)`；此时本帧车标与镜头的 setData 已被收集发出，不再互相抢时间。带 `sessionId` 校验，播放已停止则跳过。
  3. `POLYLINE_RENDER_INTERVAL_MS` 由 500 放宽到 **1000**：折线只需让"已走/未走"分界大致跟上，车标本来就压在分界前面，两者最多差一根线宽，没必要和车标同频。
- **重要约定（写给后续维护）**：像素死区要用**亚像素**（0.5px 量级），不能用"肉眼勉强看不见"（2px）当标准 —— 后者在低频下发下就是可见的顿挫。另外，折线这类 O(n) 的重绘**绝不能放在动画帧的关键路径上**，否则会周期性推迟车标下发。
- 校验：三平台条件编译预处理后括号配平通过（`paren=2` 仍为注释内中文圆括号导致的既有误报，与基线一致）；微信端新增符号未泄漏到 App 分支；App 端仍用未抽稀的 `toMpPoints()`，行为不变。

## 第四轮：修复"车标仍一顿一顿"+"蓝线到终点但车标还差一段"+"不闪动地实现高频下发"

### 问题 1 根因：66ms 时间闸门与 50ms 帧栅格不对齐（节流失配）

- 第三轮引入的 `MARKER_MIN_PUSH_INTERVAL_MS = 66`（约 15Hz 上限）与 `PLAYBACK_FRAME_INTERVAL_MS = 50`（20Hz）**不在同一栅格上**：66 落在相邻两帧中间，导致刚推完的那一帧必然撞上 `elapsed < 66` 被拦下，实际频率被压成 **100ms/次（10Hz）**。
- 而镜头是每帧 20Hz。**两者节奏失配就是"车标一顿一顿"的直接原因** —— 底图 20Hz 平滑滑过，车标 10Hz 跳一下。
- **改法**：删掉 `MARKER_MIN_PUSH_INTERVAL_MS` 与 `shouldPushMarkerPosition()` 里的时间闸门，只保留**纯位移死区**（`MARKER_MOVE_DEADBAND_PX = 0.5`）+兜底（`MARKER_FORCE_PUSH_INTERVAL_MS = 250`）。车标与镜头重新同频 20Hz。
- 实测（zoom 16~17、60~120km/h）：间隔由 100ms → 50ms（**10Hz → 20Hz**），单次跳动由 1.60~3.21px → 0.80~1.60px。

### 问题 3 的解法：靠"减轻单次下发内容"而不是"降低下发频率"来防闪动

- 之前的防闪动思路是**降频**，但降频直接换来卡顿——这是一对矛盾。
- 关键认识：闪动的本质是**单次重建的视图数**，不是频率。微信端每收到一次 `markers` 就销毁重建整个 marker 覆盖物层，**重建成本与数组里 marker 数量、每个 marker 挂多少 callout 成正比**。
- 原数组是 `[车标, 起点+callout, 终点+callout]` → 每次下发重建 **3 个视图 + 2 个气泡**。
- **改法**：新增 `PLAYBACK_MARKER_LITE = true`（`#ifdef MP-WEIXIN`）。播放期间 `applyPlaybackLiteMarkers()` 只下发车标 1 个 marker，**单次重建成本降到约 1/3**；暂停/结束时由 `applyFullMarkers()` 把起终点补回。为此把 `initCarMarker()` 里的 `startMarker` / `endMarker` 从局部变量提为外层 `let` 引用，否则播放中被剔除后无法补回。
- 这样车标得以**在 20Hz 下发的同时不闪**，问题 1 与问题 3 同时解决。

### 问题 2 根因：播放结束时最后一帧被死区拦下，且此后不再有帧来补正

- `finishPlayback()` → `pausePlayback()` 会 `clearPlaybackTimer()`，**定时器清空后不再有帧**。而最后一帧的 `updateCarPosition()` 可能被 `shouldPushMarkerPosition()` 拦下（距上次下发不足死区/兜底），于是**车标永久停在最后一次推送的位置**；而 `updatePolyline()` 不受该节流约束，直接把蓝线画到终点 → **蓝线已到终点、车标还差一小段**。倍速越高、末段越短，越容易被触发。
- **改法（三处强制对齐）**：
  1. `updateCarPosition()` 增加 `force : boolean` 参数，`force = true` 时跳过节流。函数签名改为 `updateCarPosition(force : boolean)`，三个调用点全部显式传参：`renderPlaybackIndex()` 与 `pausePlayback()` 传 `true`，动画帧内传 `false`。
  2. `renderPlaybackIndex()`：这是"跳变后的确定值"（段末 / 重置 / 载入完成），改为 `updateCarPosition(true)`。
  3. `pausePlayback()`：暂停与播放结束的共同出口，在此 `resetMarkerPushTracking()` + `updateCarPosition(true)` + `applyFullMarkers()` 一次性收尾对齐（车标强制到位 + 起终点补回）。
- 效果：车标与终点差距从"最多 66ms 的位移（倍速 30x 时末段仅 16.7ms，差距最明显）"降为 **0**。

### 本轮重要约定（写给后续维护）

1. **节流阈值必须与帧间隔对齐**。像 `MARKER_MIN_PUSH_INTERVAL_MS = 66` 这种"独立取值"会与 50ms 帧栅格产生拍频，把 20Hz 压成 10Hz 而非预期的 15Hz。要限频就让阈值等于帧间隔的整数倍，否则干脆不设时间闸门、只用位移死区。
2. **"防闪动"与"防卡顿"在微信小程序地图上是对立的**，必须换维度破局：不要靠降频防闪，而要靠**减少单次下发的视图数**（播放时剔除静止的起终点 marker 及其 callout），从而在高频下也不闪。
3. **镜头与覆盖物的节流门控必须分离**，且**任何"清空定时器"的收尾路径都要强制补正最后一帧**——否则会出现"动画已结束、图形差一小段"的永久性错位。

### 校验

- 三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译预处理后括号配平通过（`paren=2` 仍为校验器把注释内中文圆括号计入的既有误报，与 `git show HEAD:` 基线一致）。
- 微信端新增符号（`applyFullMarkers` / `applyPlaybackLiteMarkers` / `startMarker` / `endMarker`）在 App 分支均可见且不依赖微信端常量；`PLAYBACK_MARKER_LITE` 与 `applyPlaybackLiteMarkers` 已包进 `#ifdef MP-WEIXIN`，剥离注释后确认**未泄漏到 App 分支**。

## 第五轮：车标闪动的根治（放弃 markers 路线，改用 cover覆盖物）

### 为什么前三轮的所有努力都不可能成功

- 用户反馈：车标与镜头已完全同频、结束精确落在终点、暂停后起终点正常，但**车标仍在长距离直线段不停闪动**。
- 根因（三轮方案的共同天花板）：**闪动的物理来源只有一个 —— 微信小程序端每收到一次 `markers` 赋值，安卓原生 SDK 就销毁并重建整个 marker 覆盖物层**，那一帧的销毁残留就是闪动。
- 前三轮用的都是"**降频 + 减轻单次重建成本**"（像素死区、时间闸门、`PLAYBACK_MARKER_LITE` 剔除起终点）。这些只能让闪动**变少**，无法让它**归零**，因为"重建"这个动作本身从未被取消。
- 为什么偏偏是长距离直线段最明显：直线段车速高 → 每帧位移远超 0.5px 死区 → **每一帧都必然越过死区、每帧都下发** → 闪动频率达到理论上限（20 次/秒）。这恰好是前几轮参数调优无法覆盖的最坏工况。

### 本轮方案：把播放期车标整体移出原生 markers 图层

- 关键突破：**车标根本不需要是 marker**。播放时车标恒定位于屏幕正中，那么它可以是一个**普通 `view` 覆盖物**（`.car-overlay` + `image`，50rpx 见方，`position:absolute` 四边贴合 + flex 居中），盖在 map 之上。
- 可行性依据（已核实）：uni-app x 官方文档明确 `cover-view` 在 **app / web / 微信小程序上已废弃，直接用 `view` 即可**（微信基础库 2.8.3 起 map 支持同层渲染）；且本项目 `sub-navBar`（`z-index:100` 的普通 view）本来就压在 map 之上正常显示，编译产物 `playBack.wxml` 证实它是 map 的**兄弟节点**而非子节点 —— 同层渲染在本项目已验证可用。
- 于是播放期的职责彻底分离：
  - **只有地图在动**（`center` 每 50ms 下发两个数字，极轻、不触发覆盖物重建）；
  - **车标钉在正中不动**，视觉上二者完全同频；
  - **`markers` 数组在整个播放过程一次都不再被赋值** → 安卓端零图层重建 → **闪动彻底消除**。
- 车标朝向仍需变化，因此覆盖层保留 `transform: rotate()`，用 2° 死区（复用 `MARKER_ROTATION_UPDATE_THRESHOLD`）。直线段朝向恒定，连这点 setData 都不会发生。

### 代码改动要点

- 模板：`map` 之后、`sub-navBar` 之前新增 `#ifdef MP-WEIXIN` 的 `.car-overlay`；新增 `showCarOverlay` / `carOverlayIcon` / `carOverlayRotation` 三个状态。
- `updateCarPosition()`：在 `if (isPlaying)` 更新 center 之后**立刻插入提前 `return`** —— 播放期只刷覆盖层朝向，完全不碰 `markers`。这是全文件最关键的一处改动。
- `startPlayback()`：`showCarOverlay = true` + `carOverlayRotation = 当前角度` + `markers.value = markers.value.slice(1)`（剔除原生车标，保留静止的起终点）。交接发生在同一帧，视觉无缝。
- `pausePlayback()`：`showCarOverlay = false` + `updateCarPosition(true)` + `applyFullMarkers()`。**关键**：必须先让原生 markers 车标精确落到最后一个渲染点，否则覆盖层消失后会看到车标错位一小段。
- `renderPlaybackIndex()` 的 `if (!isPlaying.value) applyFullMarkers()` 守卫是**正确且必须保留**的 —— 播放中一旦在这里把车标补回 `markers`，闪动立刻回来。
- 新增 `shortestAngleDiff(from, to)` 工具函数（环形量按最短路径比较，-180~180）。原先 359°→1° 会被误判为 -358° 转角，导致每帧都触发朝向重绘。
- 清理了彻底失效的符号：`shouldPushMarkerPosition()` / `markMarkerPositionPushed()` / `resetMarkerPushTracking()` / `PLAYBACK_MARKER_LITE` / `applyPlaybackLiteMarkers()` / `MARKER_MOVE_DEADBAND_PX` / `MARKER_FORCE_PUSH_INTERVAL_MS` 及配套的 `lastPushedLat` 等变量。`getMetersPerPixelOfScale()` 暂无调用方但保留（视野计算相关，可能复用）。

### 本轮最重要的一条工程结论（写给后续维护）

1. **在微信小程序地图上，"防闪动"和"防卡顿"无法靠调参同时满足** —— 因为闪动源于 `markers` 的**原生图层重建**，而降频必然带来滞后与顿挫。唯一的出路是**换维度：让需要高频变化的东西彻底离开原生覆盖物图层**。
2. 判断某个视觉元素该不该留在 `markers` 里，标准是：**它是否需要高频变化**。需要高频变化（车标、跟随光标）就不要放进 `markers`；静止不动的（起终点、气泡、POI）才适合。
3. 由此可推广：地图上凡是"位置高频变化 + 视觉上可以由容器定位表达"的东西，都应该用**覆盖物 + 容器居中**表达，而不是原生 marker。项目里 `deviceList.uvue` 的聚合点同理，若后续也遇到闪烁，可考虑同样处理。
4. 交接（切换表示方式）必须在**同一帧**内完成，且旧表示要先精确落位再隐藏新表示，否则会出现一帧的错位。

### 校验

- 三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译**双向校验通过**：无未闭合 `#ifdef`、无多余 `#endif`（脚本对 `//`、`<!--`、`/*` 三种注释语法均做了处理，前一版脚本因正则贪婪 + 未处理 HTML 注释语法产生过误报）。
- 结构断言：程序化确认 `updateCarPosition` 内 `markers.value =` 赋值位于 `isPlaying` 提前 `return` **之后**，即播放期确实无法触达该赋值。
- 微信端新增符号未泄漏到 App 分支；App 端（Android/iOS）沿用原有 markers 路线，行为完全不变。
- 括号配平 `paren=2` 与 `git show HEAD:` 基线数值完全一致，为校验器把注释内中文圆括号计入的既有误报。
- **需真机验证**：安卓微信端播放时车标是否完全不闪；直线段是否丝滑；暂停/结束时覆盖层与原生车标是否无缝衔接。

## 第六轮：修复"线路闪烁"+"蓝线跟不上车标"（折线重绘机制重构）

### 背景：第五轮车标闪动已解决，本轮两个问题都在折线上

- 用户确认：安卓微信端车标**完全不闪**、直线段丝滑。但新反馈两点：
  1. **线路在闪烁**（车标已不闪，但整条轨迹线还在闪）；
  2. **蓝线跟不上车标**——车速快时车标已经走出去，蓝色实线才渲染出来，慢一点点。

### 关键判断：这两个问题是同一个参数的两面，调参无解

- 上一轮为解决"车标闪动"把 `POLYLINE_RENDER_INTERVAL_MS` 设为 **1000ms**，本轮这两个问题**正是由它一手造成**：
  - 每 1000ms 跨线程重传一次整条轨迹 → 安卓端每秒重建一次 polyline 图层 → **线路闪一下**；
  - 两次刷新之间车标已走出去很远 → **蓝线明显滞后**。
- **这是死结**：调小则闪烁更频繁（20Hz 重建 = 持续闪烁），调大则滞后更明显。**必须改实现方式，而不是调参**。

### 真正的根因：抽稀基准不稳定（此前从未被发现）

- 原实现每次重绘都对"已走子集"和"未走子集"**各自重新抽稀**：
  ```ts
  points: toThinnedMpPoints(unplayedPoints)   // 按未走子集头尾均分
  points: toThinnedMpPoints(playedPoints)     // 按已走子集头尾均分
  ```
- 两个子集的**取点基准完全不同**，于是同一条路在不同时刻落点不同 → 视觉上整条线在轻微抖动；叠加安卓端每次 polyline 赋值的图层重建，就成了用户看到的"闪烁"。
- 这解释了为什么此前把间隔从 500 调到 1000 只能缓解、改不掉——**抖动来自抽稀本身，重建只是把它放大成可见闪烁**。

### 本轮改法（`#ifdef MP-WEIXIN`）

1. **整条轨迹只抽稀一次**，结果缓存为两个平行数组：
   - `thinnedSourceIndex : Array<number>` —— 每个抽稀点对应的原始下标，播放时按 `currentIndex` 定位分界；
   - `rawPoints : Array<MapPolylinePoint>` —— 每个抽稀点的纯经纬度，画线时直接复用。
2. **每帧只做 slice，不再新建点对象**：
   - 灰线（未播放）= `rawPoints.slice(boundary + 1)`（后缀）；
   - 蓝线（已播放）= `rawPoints.slice(0, boundary + 1)`（前缀）+ **追加车标实时插值位置**。
   - 每帧真正新建的对象只有"车标实时位置"这**一个**，CPU 开销从 O(原始点数) 降到 O(抽稀后点数)。
3. **蓝线末端追加车标实时位置**（`needLivePoint` 判断，与末点重合时不重复追加）——这是"蓝线跟得上车标"的关键：无论车标落在哪个抽稀点之间，蓝线都精确追到车标脚下。
4. `POLYLINE_RENDER_INTERVAL_MS` 由 **1000 → 50**（与帧同频）。之所以敢提到 20Hz，是因为第 2 条把单次重算成本降到了一个对象；此前 1000ms 是"为了不闪而牺牲跟手"的无奈妥协。
5. 删除 `toThinnedMpPoints()`、`thinnedPoints` / `ThinnedPoint` 类型、`toMpRawPoints()` 等中间层。

### 过程中的一次自我纠错（重要）

- 我最初把灰线改成"全长绘制"（企图让灰线变成静态线、只下发一次），但立刻发现这是**错的**：全长灰线 + 前缀蓝线 = 单次下发点数变成 `N + 已走`（最多 2N），**比原来多一倍**，会让闪烁更严重。已回退为"灰线=未走后缀、蓝线=已走前缀"，两者点数之和恒为 N，与原实现持平。
- 教训：**优化前先算清单次下发的数据量**，不能只看"是否变成静态引用"。

### 本轮工程结论（写给后续维护）

1. **"防闪烁"与"防滞后"在微信小程序地图上无法靠调同一个参数同时满足**，必须降低单次重算/重传的成本，才敢提高刷新频率。顺序是：**先降成本，再提频率**；反过来（先提频率再砍成本）只会更卡。
2. **抽稀必须"一次抽稀、全程复用"**。任何"对子集重新抽稀"的写法都会让线形随播放抖动 —— 这类 bug 在 App 端不明显（原生渲染路径不同），只在微信端暴露。
3. **累计量恒定 vs 峰值量翻倍**：把一条线改"全长"看似减少了重绘次数，实际让单次 payload 翻倍，得不偿失。
4. 线段末端追加"实时插值点"是让图形跟上车标的通用手法，与第五轮的"覆盖层车标钉在中心"是同一思路的延伸：**高频变化的部分要用最小代价表达**。

### 校验

- 三平台（MP-WEIXIN / APP-ANDROID / APP-IOS）条件编译双向校验通过（无未闭合、无多余 `#endif`）；微信端抽稀符号（`rawPoints` / `thinnedSourceIndex` / `buildThinnedPoints`）未泄漏到 App 分支。
- `ThinnedPoint` 类型已随中间层一并删除，仅在注释说明文字中提及（无代码引用）。
- 括号配平：大括号 / 方括号完全一致；小括号差 2 与 `git show HEAD:` 基线数值完全一致，为校验器把注释内中文圆括号计入的既有误报。
- App 端（Android/iOS）折线逻辑与 `POLYLINE_RENDER_INTERVAL_MS = 80` 均未改动，行为不变。
- **需真机验证**：① 线路是否不再闪烁；② 蓝线末端是否始终精确压在车标脚下（尤其 20x/30x 倍速）；③ 灰线与蓝线交界处是否有残留灰点。

## 第七轮：修复"车标前方一小段虚线消失"（灰线起点覆盖漏洞）

### 现象

- 车标仍在播放中，但**车标前方的一小段灰色虚线已经消失**，路线在车标前方断开一截。
- 期望：灰色虚线保持完整（一直延伸到终点），车标走过的地方被蓝色实线覆盖。

### 根因：这是一个几何覆盖漏洞，与刷新频率无关

第六轮的实现里，两条线的分工是：

- **蓝线** = `rawPoints.slice(0, boundary + 1)` + 车标实时位置 → 末端精确落在车标脚下
- **灰线** = `rawPoints.slice(boundary + 1)`（抽稀点的后缀）→ 起点是**下一个抽稀点**

其中 `boundary` 是"sourceIndex <= currentIndex 的最后一个抽稀点"。

**问题在于车标绝大多数时间落在这两个抽稀点之间**（抽稀后相邻点可相隔数百米）。此时：

```
rawPoints[boundary]  ←── 蓝线止于此
      ⋮  车标实际在这里移动（这段两条线都没覆盖）
rawPoints[boundary+1]  ←── 灰线起于此
```

于是"车标 → 下一个抽稀点"这一段**两条线都不绘制**，屏幕上就是一段空白 —— 即用户看到的"车标还在走，前方一小段虚线消失了"。

它与抽稀点数、刷新频率都无关：**抽稀越稀、点间距越大，缺口越长**。

### 修法：把车标实时位置接到灰线**头部**

灰线起点改为车标实时位置（而非下一个抽稀点）：

```ts
const livePoint : MapPolylinePoint = { latitude: renderedPoint.latitude, longitude: renderedPoint.longitude }
const grayPoints : Array<MapPolylinePoint> = []
if (needLiveHead) grayPoints.push(livePoint)          // 车标位置作为灰线起点
for (let i = Math.max(boundary + 1, 0); i < thinnedCount; i++) grayPoints.push(rawPoints[i])
```

蓝线继续以 `livePoint` 收尾 —— **两条线在同一实例上精确相接**，车标脚下永不断线。效果严格等价于"全长灰线 + 前缀蓝线"。

### 关键设计决策：为什么不做"全长灰线"

用户的需求字面上是"灰线条不动"。全实现法（灰线 = 整条`rawPoints`，蓝线 = 前缀）视觉上完全相同，但**单帧下发点数会从 ~N 变成 ~2N**：

- N=400 抽稀点 → 全长灰线方案单帧最坏 800 点
- 本方案（灰线从车标起）单帧恒定 ~402 点（模拟实测）

**车标身后那段灰线本来就完全被同宽蓝线盖住，下发它是纯浪费。** 这一点正是第六轮我曾因payload 翻倍而回退的原因；本轮用"起点偏移"而非"全长绘制"同时满足了正确性与开销约束。

另外 `livePoint` 是**灰蓝两线共用的同一个对象实例**，每帧只新建 1 个点对象（原实现蓝线单独新建 1 个，灰线不建；现在总额仍为 1）。

### 重复点防护

车标恰好落在抽稀点 `boundary` 上时，`needLiveHead` 为 false，不重复添加同一点（否则会产生长度为 0 的线段，某些渲染库会异常）。已模拟验证：车标恰在抽稀点 100 时 `needLiveHead=False`。

### 顺带清理

- 删除第六轮遗留在微信端 `updatePolyline` 中的未使用局部变量 `isAnimatingSegment`（改用灰线起点方案后不再需要；App 端同名变量仍在用，未动）。
- 修正第六轮 `POLYLINE_RENDER_INTERVAL_MS` 上方的注释——原文写"灰色底图变为整条轨迹的静态线、全程只下发一次"，与实际实现（灰线为后缀）已不符。

### 校验

- 三平台条件编译双向校验通过，微信端专有符号（`livePoint` / `grayPoints` / `needLiveHead`）未泄漏到 App 分支。
- 括号配平：大括号/方括号完全一致；小括号差 2 与 `git show HEAD:` 基线完全一致（校验器把注释内中文圆括号计入的既有误报）。
- **Python 模拟验证**：1000 点轨迹（抽稀至 400）+ 50 点短轨迹，覆盖起播/中段/段中/终点/恰落抽稀点等 8+ 个关键帧，逐帧断言"灰线首点 == 车标"且"蓝线末点 == 车标"，全部通过；单帧合计点数稳定在 401~402（而非全长方案的 ~800）。

### 工程结论

1. **"跟随渲染"类图形必须显式衔接分界**：两条线交接时，交接点必须**同时是前者的末点和后者的首点**，且用同一坐标（最好同一对象实例）。只对齐"蓝线末端→车标"而放任"灰线起点"停在抽稀点上，必然留下缺口。
2. **视觉等价不等于实现等价**："全长底图 + 增量覆盖"与"底图从当前位置起绘"视觉完全一致，但后者payload 只有一半。凡是"被覆盖部分不可见"的部分，都不该下发。
3. 抽稀会**放大**这类漏洞：点越稀、缺口越长，所以抽稀策略与线条分段策略必须一起设计。

## 第八轮：修复"播放前虚线残缺"（非播放态灰线脱离 boundary）

### 现象（用户截图）

- 图一（**播放前**）：灰色虚线只有上半截，下半截凭空消失，整条路线不完整。
- 图二（**播放中**）：虚线完整，且蓝线正常覆盖已走部分——上一轮的修复在播放态是有效的。
- 用户明确需求：**灰色虚线条不动**（全长恒定），车标走过的地方被蓝色实线覆盖。

### 根因：灰线起点依赖 `boundary`，而非播放态下该值不可靠

第七轮的实现里，灰线**统一**走"从车标位置往后接"的后缀分支：

```
grayPoints = [livePoint] + rawPoints.slice(boundary + 1)
```

其中 `boundary` = 最后一个满足 `thinnedSourceIndex[i] <= currentIndex` 的抽稀点。

- **播放中**：`currentIndex` 随动画推进，boundary 正好落在车标附近，灰线起点=车标 → 视觉正确。
- **非播放态**：`currentIndex = 0`，`boundary` 被压到最前端（=0），灰线起点变成"车标前方那一个抽稀点"，
  于是**车标所在位置到该抽稀点之间的整段没有任何线绘制**——这就是图一缺失的那一截。

关键点：这个缺陷**与车标是否在动无关**，纯粹是"用动态边界驱动静态图形"这一设计本身的问题。

### 修法：按播放状态分流，非播放态完全不依赖 boundary

```ts
let grayPoints : Array<MapPolylinePoint> = rawPoints   // 非播放态：整条抽稀结果，零拷贝
if (isPlaying.value) {
    grayPoints = []                                    // 播放态：只画车标前方的后缀
    if (needLivePoint) grayPoints.push(livePoint)
    for (let i = Math.max(boundary + 1, 0); i < thinnedCount; i++) grayPoints.push(rawPoints[i])
}
```

两种走法**视觉结果完全一致**，但适用场景不同：

| 状态 | 灰线取法 | 点数 | 说明 |
|---|---|---|---|
| 非播放（查出轨迹 / 回到起点 / 暂停） | `rawPoints` 全长 | N | 静止状态，只下发一次，无开销；且**完全不依赖 boundary**，杜绝残缺 |
| 播放中 | `[livePoint] +后缀` | ≈N | 车标身后的灰线被同宽蓝线完全遮盖，下发是浪费 |

关键权衡：**非播放态用全长是零成本的**（静止画面不需要高频刷新），而播放态坚持用后缀是为了把单帧点数压在 N 附近——若播放态也画全长会翻到 2N，必然让安卓端重新出现线条闪烁。这两个决定看似矛盾，实则由"是否需要高频刷新"区分。

### 顺带修正

- `needLiveHead` 改名为 `needLivePoint`，并**提到 `if (isPlaying)` 块外**。
  原因：它同时被播放态灰线与**块外**的蓝线使用，若留在块内属跨作用域引用（UTS 编译期会报错）。
  变量含义也已泛化为"两条线是否都需追加车标点"。
- 修正 `livePoint` 的过时注释（它只在播放态被使用）。

### 校验

- 三平台条件编译双向校验通过，微信端专有符号（`grayPoints` / `needLivePoint` / `livePoint` / `rawPoints`）未泄漏到 App 分支。
- 括号配平：大括号 / 方括号完全一致；小括号差 2 与 `git show HEAD:` 基线一致（校验器把注释内中文圆括号计入的既有误报）。
- 作用域断言：`needLivePoint` 定义位置 < 播放态引用 < 蓝线引用，全部正确；旧名 `needLiveHead` 无残留。
- **模拟验证**（1000 点轨迹抽稀至 400）：
  - 播放前灰线覆盖抽稀点 **400/400**（修复前为 399/400），未覆盖 = 无；
  - 播放中各关键帧（起播/段中/中段/终点）灰蓝合计恒为 **400~402 点**，与修复前持平，未增加通信量；
  - 回到起点后灰线恢复 400/400。

### 工程结论

1. **不要用动态状态驱动静态图形**。非播放态的折线边界与车标位置无关，绑上去反而引入缺陷。判据：图形是否在动。
2. **"视觉等价"的两种实现，通信量可以差一倍**，取舍依据是刷新频率：静止状态用最完整的表达（零成本），高频刷新状态用最省的表达。这与上一轮"全长灰线会翻倍"的结论并不冲突——**前提是先分清状态**。
3. 跨作用域变量提取要一并检查：把常量从 `if` 块里"优化"出去时，必须确认块外也在用它。

## 第九轮：播放中线路闪烁（死结的最终解法）

### 现象与约束

用户反馈四项，其中三项已确认正常、**不得回归**：

1. 线路还在闪烁 ← 本轮唯一待解
2. ✅ 查询出轨迹后虚线完整贯通到起点
3. ✅ 播放中灰线随车标前进、蓝线精确覆盖已走段、无断口
4. ✅ 暂停后仍是完整灰线

### 根因

与第六轮诊断一致：**`updatePolyline()` 在播放中每 50ms（20Hz）整体替换 `polyline` 数组，微信端安卓每次收到赋值都销毁重建整条折线图层**，重建期间旧图层已撤、新图层未就位的那一帧就是闪烁。`livePoint`（车标实时位置）的存在强制要求每帧重绘，所以无法简单地"少更新"。

**与车标闪动的关键差异**：车标可以移出原生图层（改成 `.car-overlay` 普通 view 覆盖物，已在前几轮完成，因此车标闪烁被彻底消除）；但**折线必须画在地图坐标系上，移不走**。所以只剩"降频"一条路。

**此前调参无解的原因**：
- `POLYLINE_RENDER_INTERVAL_MS = 1000` → 每秒重建一次，仍闪；且两次刷新间车标走几百米，蓝线严重滞后。
- 调成 50ms → 蓝线跟上了，但退化成 20Hz 重建，闪烁更明显。

即"闪烁"与"滞后"在**时间闸门**这个维度上此消彼长，是死结。

### 解法：用屏幕位移死区替代时间闸门

**破局点**：播放期车标是钉在屏幕中心的 `.car-overlay` 覆盖物，图标 `50rpx`（≈25px，半径约 12px）。只要两次重绘之间车标在**屏幕上**移动不超过 8px，那截"蓝线末端暂时落后于车标"的空隙就完全落在图标底下，肉眼看不到。灰色虚线同理（起点是同一个 `livePoint`）。

于是降频不再以滞后为代价 —— **两个目标第一次不再冲突**。关键在于：时间闸门是"物理时间"维度，而遮挡只关心"屏幕像素"维度；换到后者，倍速与缩放的影响被自动归一化。

实现（全部在 `#ifdef MP-WEIXIN` 内）：

| 符号 | 作用 |
|---|---|
| `POLYLINE_SCREEN_DEADBAND_PX = 8` | 基准死区（px） |
| `POLYLINE_MIN_PUSH_GAP_MS = 200` | 自适应下限约束：两次重绘至少间隔这么久（> 安卓重建耗时） |
| `POLYLINE_MAX_DEADBAND_PX = 64` | 死区上限；**"闪烁优先于滞后"的显式取舍** |
| `polylineAnchorLat/Lng/Scale/Valid` | 上次真正下发时的车标位置与缩放级别 |
| `polylineDeadbandPx` / `polylineLastPushAt` | 当前生效死区 / 上次下发时刻 |
| `getScreenDistancePx()` | 两点间地面距离 → 当前缩放下的屏幕像素（复用已有的 `getMetersPerPixelOfScale()`） |
| `shouldPushPolyline()` | **纯判定、无副作用** |
| `markPolylineRendered()` | 记录锚点 **+ 自适应更新死区**（只在真正下发后做） |
| `invalidatePolylineAnchor()` | 作废锚点并强制下一次下发，死区回基准值 |

### 两个关键实现陷阱（都已踩过并修正）

1. **`shouldPushPolyline()` 绝不能有副作用**。它每帧会被调用**两次**：帧循环里决定要不要排延迟任务、`updatePolyline()` 内部再确认一次。初版把"自适应抬高死区"写在判定里，结果第二次判定因死区已被抬高而误判"还没走够"，**把本次重绘吞掉**。改为：判定纯读，自适应只在 `markPolylineRendered()`（真正下发后）执行。
2. **`renderPlaybackIndex()` 不能在播放态无条件强制重绘**。它每段末都会调用（长轨迹下可达 2~3Hz），强制下发等于把闪烁请回来。改为 `if (!isPlaying.value) invalidatePolylineAnchor()`——播放态段末位置与上一帧插值位置是连续的（车没有瞬移），交给死区即可；真正跳变的入口（起播/暂停/重置/拖动/换轨迹）各自显式 invalidate。

### 强制对齐清单（`invalidatePolylineAnchor()` / 强制 `updatePolyline()`）

- 起播 `startPlayback()`：否则起播瞬间看到蓝线落后一小段再跳回。
- 暂停 `pausePlayback()`：播放中最后几帧可能被死区跳过，而暂停后车标要交还原生 markers，必须精确对齐。
- 非播放态 `renderPlaybackIndex()`（重置 / 拖动进度 / 载入完成）。
- `clearTrackDisplay()`：换轨迹。
- `initPolyline()`：装载后首绘。
- 缩放级别变化：`shouldPushPolyline()` 内比对 `polylineAnchorScale != mapScale.value` 自动作废锚点（像素↔米换算关系变了，旧锚点位移不可信）。

### 仿真验证（30~120km/h，scale 12~17，1x~128x）

| 场景 | 重绘频率 | 死区 | 最大蓝线落后 | 判定 |
|---|---|---|---|---|
| 1x + 最高缩放(17) | 0.87 Hz | 8.0px | 8.1px | 图标遮住 |
| 8x + scale 17 | 2.17 Hz | 8.0px | 8.6px | 图标遮住 |
| 32x + scale 17 | 2.73 Hz | 8.0px | 8.4px | 图标遮住 |
| 64x + scale 17 | 3.37 Hz | 8.0px | 8.3px | 图标遮住 |
| 128x + scale 16 | 1.67 Hz | 8.0px | 8.3px | 图标遮住 |
| 1x + 全览(scale 5~10) | 0.00 Hz | 8.0px | ≤6.5px | 图标遮住 |

- 修复前恒为 20Hz；修复后 **0~3.4Hz（降 6~∞ 倍）**，而最大滞后恒定 ≤8.6px < 图标半径 12px。
- 自适应分支实际很少触发（截图组合下死区始终维持 8px），属安全兜底而非主要机制。
- 1x + 全览缩放下 30 秒内**一次都不重绘** —— 这正是"闪烁的物理成因是不重建"，最直接的体现。

### 校验

- 三平台条件编译：微信端 1583 行 / APP-ANDROID 1281 行 / APP-IOS 1269 行，`#ifdef`/`#endif` 全配平。
- 大括号 `{}`、方括号 `[]` 三平台均差 0；小括号差 2 已定位为校验器把 `.replace(/\//g, '-')` 正则字面量误当注释的既有误报，与基线一致。
- 符号隔离：微信端专有符号（`shouldPushPolyline` / `invalidatePolylineAnchor` / `markPolylineRendered` / `polylineDeadbandPx`）未泄漏到 App 分支；`POLYLINE_RENDER_INTERVAL_MS` 只存在于 `#ifdef APP-ANDROID || APP-IOS`。

### 工程结论（补充第八轮）

1. **"降频"不必以"精度"为代价，只要找到正确的降频维度**。时间→像素是关键换维：遮挡、覆盖、错位这些视觉现象都发生在像素空间，而跨线程开销与重建次数线性相关。用像素死区替时间闸门，是把"两件冲突的事"放进同一个空间度量后自动和解。
2. **副作用与判定必须分离**。任何"判定函数"若同时改状态，就会在被多处调用时产生非预期耦合（本次差点让重绘被自己吞掉）。
3. **"优化"要区分连续量与跳变**。段末位置是连续的（可交给死区），起播/暂停/拖动是跳变（必须强制对齐）。无脑"关键点都强制"会把优化彻底抵消。
4. **显式取舍要写进常量注释**。`POLYLINE_MAX_DEADBAND_PX` 的存在即声明："宁可滞后，不容闪烁" —— 让未来的调参者知道这是决定而非疏漏。

## 第十轮：闪烁解决了，但蓝线不再实时覆盖 —— 死区被"放大"了

### 用户反馈

> 闪烁的问题基本解决，新的问题是：车标已经运动到下一个位置，蓝色的实线并没有实时覆盖已走过的路。
> 难道路线闪动和蓝色实线无法实时覆盖不可兼得吗？

截图特征：车标（蓝色圆形）已前进到路口，**它后面是一段明显的灰色虚线**，蓝色实线远远落在左后方，两者之间隔着上百像素。

### 根因：不是"取舍"，是换算被放大

第九轮的死区是**像素**量纲：`movedPx = 地面距离 / 米每像素`。而米每像素由缩放级别决定，代码里用的是 `mapScale.value`。

**致命点：`mapScale` 是"我们命令地图去到的缩放级别"，不是"地图当前实际渲染的缩放级别"。**
用户双指放大地图后，地图自行改了 zoom，而 `mapScale` 停留在旧值上（项目里没有 `regionchange` 监听）。于是：

| | 真实 | 代码算的 |
|---|---|---|
| 缩放级别 | 17 | 12（陈旧） |
| 米/像素 | 1.03 | 33.1 |
| 死区 8px 等于 | 8 真实像素 | **256 真实像素** |

而 `POLYLINE_MAX_DEADBAND_PX` 当时是 **64**，再乘 16 倍放大 → 最坏可达上千像素。这正好解释了截图里那段灰色空档：**它不是渲染失败，是"车已经开过去了，那一段还停留在上一次重绘时的位置"**。

### 为什么第九轮的仿真没发现

仿真里 `mapScale` 与真实 zoom 始终相等。而这个 bug **只在用户手动缩放后才出现**——也就是说，只在真机上、在人放大地图之后才暴露。这是纯仿真覆盖不到的盲区，教训是：**换算类参数必须区分"指令值"与"设备真值"，不能假设二者一致。**

### 修复：三件事，缺一不可

**1. 用地图自报的真值做换算**
- `MapContext.getScale()`（微信小程序端可用，`node_modules/@dcloudio/types/.../MapContext.d.ts:29` 有声明；本项目 `deviceList.uvue` 已在用 `createMapContext`，有先例）
- 新增 `trueMapScale` + `syncTrueMapScale()` / `startMapScaleSync()`（播放期每 300ms 轮询）/ `stopMapScaleSync()`
- `getMetersPerPixelOfScale()` 改为优先用 `trueMapScale`，取不到才回退 `mapScale.value`
- 新增 `getEffectiveMapScale()` 统一口径，锚点比对也用它（原先比 `mapScale.value` 是错的）
- 真值变化时 `invalidatePolylineAnchor()`：换算关系变了，旧锚点的位移不可信，立刻重画
- 生命周期：`onReady` 先取一次；`startPlayback` 先取一次再开始轮询；`pausePlayback` / `clearTrackDisplay` / `onUnload` 停轮询并丢弃 `mapContext`（地图按 `v-if` 重建后旧 context 失效）
- `mapContext` 声明为 `any`，与 `deviceList.uvue:107` 的既有写法一致，避免 uvue 下全局声明类型的多余摩擦

**2. 死区上限 64px → 10px（必须小于图标半径）**
- 之前把"闪烁优先于滞后"写进了注释，但那是个**错误的取舍**：滞后的容忍上限由**遮挡物理**决定（图标半径约 12px），不是可以拿来换闪烁的筹码。死区一旦超过半径，蓝线末端就露在图标外。
- 第九轮写"闪烁优先于滞后"本身是错的表述，本轮改为"滞后不可超上限，超了就要从成本上解决"。

**3. 播放期裁剪屏外折线 —— 这才是"兼得"的关键**
- 播放期地图中心恒等于车标 ⇒ 可见地面范围是一个**以车标为中心、半径固定的圆**（视口半对角线 × 米/像素）。
- 圆外的点本来就看不见，却要占满 setData 预算、拖慢原生图层重建——**而闪烁的物理成因恰恰是"重建代价太大"**。
- 新增 `getVisibleRadiusMeters()` / `distanceToCarMeters()` / `findGrayClipEnd()` / `findBlueClipStart()`，播放期把灰线与蓝线都裁到该圆内（`POLYLINE_CLIP_MARGIN = 1.35`，`POLYLINE_CLIP_EDGE_TOLERANCE = 1.3`；越界点仅在"刚刚越界"时带上，防止轨迹稀疏间隔处被连成横穿屏幕的长直线）。
- **非播放态完全不裁剪**（灰线仍 `= rawPoints` 全长），所以第九轮用户已确认的三项——播放前虚线贯通起点、播放中灰蓝无断口、暂停后完整灰线——都不受影响。

**为什么裁剪让"兼得"成立**：
> 闪烁 ∝ 重建代价 ∝ 载荷点数；滞后上限 ∝ 图标尺寸（固定）。
> 两者的耦合点在"重绘频率"上，而裁剪把"高频重绘"与"大载荷"解耦了：
> 缩放越大 → 可见窗口越小 → 载荷越小 → 恰好此时才需要高频重绘；
> 缩放越小 → 载荷越大（甚至裁不剪）→ 但死区对应的地面距离变大 → 重绘极稀。
> 于是"死区可以一直压在 10px 以内"与"每次重建都足够快"第一次同时成立。

### 仿真验证（含 500ms 段时长下限对真实速度的钳制）

| 场景 | 重绘频率 | 死区 | 最大滞后 | 载荷（裁剪前恒 400） |
|---|---|---|---|---|
| **用户截图场景** mapScale=12 / 真实=17 | 1.32 Hz | 8.0px | **7.5px** | 181 |
| mapScale=16 / 真实=19.5 | 5.00 Hz | 10.0px | **9.1px** | **34** |
| 缩放一致 scale=17 | 1.32 Hz | 8.0px | 7.5px | 181 |
| 8x / 32x / 64x（真实速度被 500ms 段下限钳到 54km/h） | 0.85 Hz | 8.0px | 8.0px | 362 |
| 128x scale=17 | 1.65 Hz | 8.0px | 8.0px | 182 |
| 50km 长轨迹 8x scale=15 | 4.25 Hz | 8.6px | 8.6px | 45 |

- **最大滞后恒 ≤9.1px < 图标半径 12.5px** —— 蓝线永远被车标遮住，不会再露馅。
- 高频场景（5Hz）载荷只有 34 点，是未裁剪的 1/12。
- 一个重要发现：**真实屏幕速度天然有上界**——`getSegmentDuration` 把每段钳在 ≥500ms，所以实际速度 = 段间距/0.5s，不会随倍速无限增长。倍速调到 128x 也不会让车标一帧飞过几十像素，这从根本上限制了"必须每帧重绘"的极端场景。（第一版仿真忽略了这个钳制，误算出 20Hz，结论偏保守。）

### 校验

- 三平台条件编译：微信 1748 / Android 1281 / iOS 1269 行，`#ifdef` 全配平，`{}` `[]` 差 0。
- 微信端专有符号（`trueMapScale` / `getVisibleRadiusMeters` / `findGrayClipEnd` / `findBlueClipStart` / `syncTrueMapScale` / `createMapContext`）未泄漏到 App 分支；`POLYLINE_RENDER_INTERVAL_MS` 仍只属于 App 分支。
- 非播放态全长分支的三处关键代码均在位（回归保障）。

### 工程结论

1. **"不可兼得"通常是伪命题：先检查两个目标是否真的在对立轴上。** 本例中"闪烁"与"滞后"在**重绘频率**上对立，但在**载荷**上并不对立——降载荷可以同时改善两者。
2. **换算参数必须区分"指令值"与"设备真值"。** `mapScale` 是指令，`getScale()` 才是真值。凡是"用某个标量做单位换算"的地方，都要问一句：这个标量是"我们要求的"还是"设备实际的"？
3. **把"上限"写进物理约束，而不是写进取舍偏好。** 第九轮的 `MAX_DEADBAND=64` 注释写的是"宁可滞后也不闪烁"，把一个**必须满足的物理约束**（≤ 图标半径）写成了**可交换的偏好**，于是没人发现它已经越界 5 倍。约束要写成不可逾越的常量 + 理由。
4. **仿真要复现真实代码里的钳制/限幅。** `MIN_SEGMENT_DURATION_MS` 这种"意外"的钳制改变了结论；仿真里不建模就会得出偏保守（甚至偏错误）的判断。
5. **可见性驱动的裁剪是地图类交互的通用优化**：相机跟随主体时，主体之外的图形不进 viewport，绘制也应该不进 payload。
